# Changelog — Cinephilium 5.8

**Дата и время среза: 29.10.2026 (Europe/Moscow, UTC+03:00)**

## 5.8 — B8: полиморфные комментарии (фильм | рецензия)

**Дата: 29.10.2026.**

### Смысл

Два разных разговора, которые не должны смешиваться:
комментарий к фильму — «финал это сон героя», комментарий к рецензии — «ты пишешь, что
сон, но посмотри на сцену в баре». Рецензия перестаёт быть монологом: под ней появляется
тред, а комментарии к фильму не засоряются обсуждением чужих текстов.

`Comment` стал полиморфным: `targetType: 'film' | 'review'` + `targetId`. Поле `filmId`
**остаётся** legacy-полем: по нему работают старый роут, профиль и агрегаты.

### API

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/api/comments` | access | `{ targetType, targetId, text, parentId? }`; без `targetType` — считается `film` (совместимость) |
| GET | `/api/comments?targetType=film\|review&targetId=…` | — | пагинация `{ items, pagination }`, корни + ответы; без `targetType` → 400 |
| GET | `/api/comments/:filmId` | — | старый роут, формат не менялся: массив, **только** комментарии к фильму |
| POST | `/api/comments/:id/like` | access | без изменений, не гейтится |

Поведение по типам цели:

- `targetType: 'film'` — гейтинг B3 как раньше: нужна любая оценка фильма, иначе
  `403 RATING_REQUIRED_FOR_COMMENT`.
- `targetType: 'review'` — гейтинг **не применяется**, оценки не нужно: обсуждаем текст,
  а не фильм. `filmId` берётся из рецензии, `filmId` из тела игнорируется.
- Оба типа проходят премодерацию `pending` → `approved`/`rejected`.

### Зафиксированные решения

- **B8/schema** — полиморфизм `targetType` + `targetId`; `filmId` не удаляется (по нему
  работают старый роут, профиль и агрегаты). Pre-validate подставляет `targetId = filmId`
  для film-комментариев, поэтому любые пути создания остаются корректными.
- **B8/legacy-read** — отсутствующий `targetType` читается как `'film'` прямо в фильтрах:
  окно «деплой → миграция» не заставляет старые комментарии исчезнуть.
- **B8/1A** — комментировать можно только опубликованную рецензию (`approved`).
  Посторонним — `404` (не раскрываем существование черновика), автору и админу —
  `403 REVIEW_NOT_PUBLISHED`. **`rejected` ведёт себя как `pending`.**
- **B8/2A** — для `targetType: 'review'` `filmId` из тела игнорируется: источник истины —
  `review.filmId` (тот же принцип, что B4/1A с `ratingId`).
- **B8/3A** — старый `GET /api/comments/:filmId` отдаёт **только** `targetType: 'film'`.
  Это не косметика: у комментариев к рецензиям `filmId` тоже заполнен, и без фильтра
  треды под рецензиями протекали бы в список фильма и дублировались.
- **B8/4A** — миграция `scripts/migrate-comment-target.js`: `targetType: 'film'`,
  `targetId = filmId`, идемпотентно, `--dry-run`.
- **B8/5A** — индексы: старый `{ filmId, createdAt }` остаётся (по нему работает старый
  роут), добавлен `{ targetType, targetId, createdAt }`.
- **B8/6A** — `Review.commentsCount` не заводим: количество считается `countDocuments`
  по индексированному полю. Денормализация — обязательство поддерживать консистентность
  во всех путях, а потребителя (тред под рецензией) это не ускоряет.
- **B8/7B** — событие в ленту создаётся только для комментариев к фильму. Комментарий
  к рецензии — ответ автору в треде, а не активность для всех (тот же принцип, что
  B7/event для лайков). Новый тип события не заводился.
- **B8/parent** — ответ обязан совпадать по `targetType`/`targetId` с родителем, родитель
  должен быть `approved` (нельзя отвечать на невидимый pending), вложенность — один
  уровень. Иначе `400`.
- **B8/compat** — POST без `targetType` трактуется как комментарий к фильму,
  `targetId` берётся из `targetId` или `filmId`. Иначе деплой B8 сломал бы комментарии
  до деплоя F-серии.

### Код и тесты

- `src/models/Comment.js` — полиморфизм, pre-validate страховка, второй индекс.
- `src/routes/comments.routes.js` — нормализация цели, гейт только для film,
  новый `GET /api/comments`, старый роут с фильтром по типу, проверки `parentId`.
- `src/routes/admin.routes.js` — в очереди виден `targetType`; `approve` создаёт событие
  только для film-комментариев.
- `src/routes/users.routes.js` — профиль отдаёт `targetType`/`targetId` у комментариев,
  иначе фронт не отличит комментарий к фильму от ответа под рецензией.
- `tests/comment-targets.test.js` — 23 теста: гейтинг только для film, комментарии
  к рецензии без оценки, pending/rejected (404 посторонним, 403 автору/админу),
  игнор `filmId`, правила `parentId`, новый и старый роуты, изоляция слоёв,
  терпимость к немигрированным, лайк, модерация (событие только для film),
  админ-очередь, видимость ника скрытого автора, миграция.
- Итого **277 тестов**, все зелёные.

### Миграция

```bash
node scripts/migrate-comment-target.js --dry-run
node scripts/migrate-comment-target.js
```

## 5.7 — B7: сердечко фильма (FilmLike)

**Дата: 29.10.2026.**

### Смысл

Четвёртая ось после «смотрел», «думаю» и «хочу посмотреть»: «мне нравится».
Сердечко — эмоция, а не суждение: можно оценить на 2/10 и лайкнуть, можно оценить
на 10/10 и не лайкнуть. Отдельная коллекция `filmlike`, одна запись на пару user+film,
не массив в `Film` и не массив в `User` (массив ломает пагинацию, `canViewProfile`
и сверку публичного счётчика).

### API

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/api/films/:id/like` | access | поставить сердечко (идемпотентно) → `200 { liked: true, likesCount }` |
| DELETE | `/api/films/:id/like` | access | снять сердечко (идемпотентно) → `200 { liked: false, likesCount }` |
| GET | `/api/films/:id` | — | добавлены `liked` (для анонима `false`) и `likesCount` |
| GET | `/api/users/:id/likes` | — | публичные «Понравившиеся»; скрытый профиль без прав → `404 PROFILE_HIDDEN` |
| GET | `/api/users/me/likes` | access | свои «Понравившиеся», без гейтинга |

### Зафиксированные решения

- **B7/1A** — «двойной клик не наказывается» реализован **разделением намерения**,
  а не toggle: `POST` = «поставь», `DELETE` = «сними». Причина: с настоящим toggle
  два одновременных `POST` — это два переключения, и второй запрос, увидев созданный
  лайк, снял бы его. Тогда результат зависит от планировщика: тест проходил в общем
  прогоне и падал в одиночном. Разделение намерения делает оба сценария
  детерминированными, без таймеров и скрытого поведения. Клиент выбирает действие
  по `liked`, который он и так получает из карточки фильма.
- **B7/2A** — лайки с `weight: 0` **не** входят в публичный `Film.likesCount`,
  но **входят** в личный `counters.filmLikes`.
- **B7/4A** — достижения не зависят от `counters.filmLikes`: в `effective` он не входит,
  новых ачивок за лайки нет, `updateAchievements` на лайке не вызывается.
- **B7/5C** — `Film.likesCount` денормализован, сверяется `scripts/reconcile-film-likes.js`.
- **B7/6=404** — публичный список при скрытом профиле и зрителе без прав отдаёт 404,
  как дневник (B-PRIVACY) и watchlist (B6). Проверка — через `canViewProfile`,
  без копии логики.
- **B7/7A** — миграция `scripts/add-film-likes-fields.js` (поля `Film.likesCount`
  и `User.counters.filmLikes`).
- **B7/8B** — `likeLimiter`: 200/час **на IP**, по аналогии с `ratingLimiter`;
  висит и на `POST`, и на `DELETE`.
- **B7/not-gated** — `POST`/`DELETE` лайка и `GET /api/users/me/likes` приватностью
  не гейтятся: свой список доступен владельцу всегда.
- **B7/event** — событие в ленту не создаётся: «X лайкнул фильм Y» — шум.
- **B7/weight** — `FilmLike.weight` — снимок `User.trustWeight` на момент лайка
  (тот же паттерн, что `Rating.weight`).
- **B7/unique** — уникальность `(userId, filmId)` это фича, а не ограничение.
- **B7/recount** — при пометке фермы **полный пересчёт** затронутых фильмов, а не
  инкремент «на количество активных лайков»: операция идемпотентна, не накапливает
  дрейф при частичном сбое и совпадает по логике с reconciliation-скриптом.
  Снятие пометки — симметрично.

### Два разных числа — не путать

| Поле | Смысл | Вес |
|---|---|---|
| `Film.likesCount` | сколько сердечек у фильма (публичный агрегат) | только `weight > 0` |
| `User.counters.filmLikes` | сколько лайков поставил человек (личный счётчик) | все, включая `weight: 0` |

Тест «два пользователя лайкнули один фильм» проверяет именно это: у фильма `2`,
у каждого в профиле `1`.

### Код и тесты

- `src/models/FilmLike.js` — индексы `{userId, filmId} unique`, `{userId, addedAt}`,
  `{filmId, weight}`.
- `src/models/Film.js` — `likesCount` (default 0, min 0).
- `src/routes/films.routes.js` — `POST`/`DELETE /:id/like`, `liked` и `likesCount`
  в карточке фильма.
- `src/routes/users.routes.js` — `/me/likes` (до `/:id/likes`!) и `/:id/likes`.
- `src/utils/filmLikesQuery.js` — общая выдача списков (вес лайка наружу не отдаётся).
- `scripts/flag-sybil-accounts.js` — теперь трогает четыре места: `User.trustWeight`,
  `Rating.weight`, `FilmLike.weight`, `Film.likesCount`; в отчёт добавлены
  `likesUpdated`, `likesRestored`, `filmsRecomputed`.
- `src/utils/counterMaintenance.js` — `filmLikes` убран из `unsupportedCounters`
  и считается по `FilmLike` (иначе `$set: { counters }` обнулил бы счётчик).
- `tests/film-likes.test.js` — 19 тестов; прогон трижды подряд без флейков.
- Итого **254 теста**, все зелёные.

### Миграции (до деплоя, обе идемпотентны)

```bash
node scripts/add-film-likes-fields.js --dry-run
node scripts/add-film-likes-fields.js
node scripts/reconcile-film-likes.js --dry-run
node scripts/reconcile-film-likes.js
```

## 5.6 — B6: watchlist («хочу посмотреть»)

**Дата: 29.10.2026.**

### Смысл

Третья ось после «смотрю» (дневник) и «думаю» (оценка): «собираюсь увидеть».
Самое дешёвое действие в системе — один клик, без оценки, дневника и текста.
Watchlist — **состояние**, а не история: на пару user+film ровно одна запись,
в отличие от дневника с пересмотрами. Это отдельная коллекция, а не массив в `User`:
массив ломает пагинацию, `populate` и лимиты.

Не гейтится ничем: ни vibe/full (B3/B4), ни модерацией, ни приватностью.
Свой список доступен владельцу всегда.

### API

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/api/watchlist` | access | `{ filmId }`; первое добавление → `201`, повторное → `200`; `{ inWatchlist: true }` |
| DELETE | `/api/watchlist/:id` | access | своё; несуществующее/удалённое → `200 { inWatchlist: false }`; чужое → `404` |
| GET | `/api/watchlist/check/:filmId` | access | `{ inWatchlist: bool }` для кнопки на странице фильма |
| GET | `/api/watchlist/user` | access | свой список, `page`, `limit` (<=100), populate + `posterUrl` |
| GET | `/api/users/:id/watchlist` | — | публичный список; при скрытом профиле без прав → `404 PROFILE_HIDDEN` |

### Зафиксированные решения

- **B6/1A** — удаление идемпотентно: несуществующая запись даёт `200` и
  `{ inWatchlist: false }`, никакого `404` и никакого `{ deleted: bool }`.
  Счётчик не уходит в минус (`incCounter` это гарантирует).
- **B6/2A** — watchlist не влияет на достижения: `updateAchievements` не вызывается,
  в `effective` не входит, отдельной ачивки нет. Намерение не кормит геймификацию.
- **B6/3B** — автоудаления из watchlist при создании `Watch` **нет**: бэк watchlist
  при этом не трогает вообще. Фильм остаётся в списке до явного удаления;
  предложение «убрать из «Хочу посмотреть»?» — задача F-серии.
- **B6/4=404** — публичный watchlist скрытого профиля без прав отдаёт `404`, как дневник
  в B-PRIVACY; проверка через `canViewProfile` из `utils/privacy.js`, без копии логики.
- **B6/5A** — миграция `scripts/add-watchlist-counters.js` явная, идемпотентная,
  с `--dry-run`; счётчик выставляется по факту из коллекции.
- **B6/6B** — лимитер `watchlistLimiter`: 200 добавлений в час **на аккаунт**
  (`keyGenerator` → `userId`, лимитер стоит после `authenticate`). Переделка на IP
  не понадобилась; `validate: false`, потому что стандартные проверки библиотеки
  рассчитаны на IP-ключ.
- **B6/not-gated** — `POST`, `DELETE`, `GET /api/watchlist/user` и
  `GET /api/watchlist/check/:filmId` приватностью не гейтятся.
- **B6/event** — событие в ленту при добавлении не создаётся: намерение, а не действие.
- **B6/unique** — уникальность `(userId, filmId)` это фича: двойной клик не наказывается,
  а гонка двух `POST` разрешается уникальным индексом (второй получает `200`, а не `409`).

### Счётчик и обслуживание

`counters.watchlist` инкрементится при создании и декрементится при удалении.
Важная находка: в `counterMaintenance` этот счётчик лежал в `unsupportedCounters`
как всегда-ноль, а `processUsers` делает `$set: { counters }` **целиком** — то есть
ближайший `migrate-counters.js` / `reconcile-counters.js` обнулил бы новый счётчик.
Поэтому `watchlist` убран из `unsupportedCounters` и считается через
`WatchlistItem.countDocuments`.

### Код и тесты

- `src/models/WatchlistItem.js` — `userId`, `filmId`, `addedAt`; индексы
  `{userId, filmId} unique`, `{userId, addedAt}`, `{filmId}`.
- `src/routes/watchlist.routes.js` — API; `src/utils/watchlistQuery.js` — общая выдача;
  `src/utils/paging.js` — общая пагинация (вынесена из дневника).
- `tests/watchlist.test.js` — 17 тестов: добавление/повтор/удаление/идемпотентность,
  чужое удаление, `check`, пагинация и `posterUrl`, приватность во всех вариантах,
  отсутствие влияния на достижения и события, независимость от `Watch`,
  лимит 201-го запроса (с ротацией IP — доказывает, что ключ на аккаунт), миграция.
- `tests/counters.test.js` — `watchlist` в ожиданиях и стаб `WatchlistItem`.
- Итого **235 тестов**, все зелёные.

### Миграция

```bash
node scripts/add-watchlist-counters.js --dry-run
node scripts/add-watchlist-counters.js
```

Коллекция `watchlistitems` новая, данных для переноса нет — создаются только индексы.

## 5.5 — B-PRIVACY: приватность профиля и ленты, Event.userId, retro-fit B5

**Дата: 29.10.2026.**

### Смысл

Два независимых флага (D1): `hideProfile` — скрыть страницу профиля, `hideFromFeed` — не
мелькать в общей ленте. Скрываются только **личные** разделы (A2): дневник, оценки,
достижения (и watchlist, когда появится). Рецензии и комментарии остаются видимыми там,
где опубликованы (C2), оценки скрытого пользователя продолжают участвовать в средних
фильмов (F1). Ник и аватар видны всегда — они и так светятся в рецензиях и комментариях.

### API

Новое:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/users/me/privacy` | текущее состояние флагов |
| PUT | `/api/users/me/privacy` | partial update `{ hideProfile?, hideFromFeed? }`, лог только при фактическом изменении |

Изменено:

| Путь | Поведение при скрытом профиле и зрителе без прав |
|---|---|
| `GET /api/users/:id` | `200` с заглушкой `{ user: { id, nickname, avatar, isHidden: true } }` |
| `GET /api/users/nickname/:nickname` | `200` с `{ id, nickname, avatar, isHidden: true }` |
| `GET /api/users/:id/achievements` | `404 PROFILE_HIDDEN` |
| `GET /api/users/:id/watches` | `404 PROFILE_HIDDEN` |
| `GET /api/events` | события авторов с `hideFromFeed` исключены |
| `GET /api/top/users` | скрытые профили исключены |

Добавлены два пути, которых не хватало B5 относительно спецификации:
`GET /api/users/:id/watches` (алиас публичного дневника) и `GET /api/watches/:filmId/count`
(`{ filmId, count }`, без фильтрации скрытых).

Скрытыми правами обладают владелец, админ и — в будущем — «друзья»
(`canViewProfile`, ветка-заглушка с `// TODO: B-SOCIAL`).

### Event.userId (вариант A)

- `Event.userId` + индекс `{ userId, createdAt }`. `user` (ник) остаётся для отображения:
  фильтровать приватность по нику нельзя, ник — отображаемое имя, а не связь.
- `createEvent` переведён на параметры-объектом, `userId` обязателен. Без автора событие
  **не создаётся** и пишет ошибку в лог: иначе появилась бы запись, которую невозможно
  скрыть по приватности.
- Обновлены все места создания событий: `rating` (новая и апгрейд), `vibe`,
  `film_add`, `comment` (одобрение), `review` (одобрение), `achievement`.
  Мест, создающих `Event` в обход `createEvent`, **не было** — единственный `Event.create`
  живёт внутри `createEvent`.
- `scripts/add-event-userid.js` — миграция по нику, идемпотентна, `--dry-run`, печатает
  число несматченных. Правило: 0 — норма, ровно 1 — осиротевшее событие пропускается
  с логом, **больше 1 — стоп** без записи и с кодом 1 (нужен разбор).

### Зафиксированные решения

- **B-PRIVACY/A2** — скрываются только личные разделы; рецензии и комментарии видны.
- **B-PRIVACY/B3+** — скрытый профиль видят владелец, админ, в будущем «друзья»;
  `canViewProfile` написан с веткой-заглушкой под B-SOCIAL.
- **B-PRIVACY/C2** — скрытие профиля не отзывает опубликованное.
- **B-PRIVACY/D1** — два независимых флага, partial update не сбрасывает второй.
- **B-PRIVACY/E2** — заглушка: только ник и аватар, без счётчиков и разделов.

## 5.4 — B5: дневник просмотров (Watch)

**Дата: 29.10.2026.**

### Смысл

«Просмотрено» ≠ «оценено». Дневник — история, а не состояние: одна запись это «я посмотрел
этот фильм такого-то числа», и на один фильм их может быть сколько угодно (пересмотры).
Поэтому это **отдельная коллекция**, а не поле в `Rating`: у оценки одна запись на пару
user+film (`unique`), у дневника множественность — фича, а не дубликаты.

Дневник не гейтится ничем: это самое дешёвое действие в системе, дешевле vibe. Vibe даёт
право комментировать (B3), full — право писать рецензию (B4), дневник открыт любому
авторизованному.

### API

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| POST | `/api/watches` | access | отметить просмотр: `{ filmId, watchedAt?, isRewatch?, tags? }` → `201` |
| GET | `/api/watches/me` | access | свой дневник, `page`, `limit` (<=100), сортировка по `watchedAt` |
| GET | `/api/watches/user/:userId` | — | публичный дневник; закрытый → `403 DIARY_PRIVATE` |
| PATCH | `/api/watches/settings` | access | `{ private: true\|false }` — закрыть/открыть дневник |
| DELETE | `/api/watches/:id` | access | удалить свою запись; чужая → 404 |
| GET | `/api/films/:id` | — | добавлено `watchesCount` — «N просмотров» |

Создание и удаление меняют `counters.watches`. Событие в общую ленту **не** создаётся.

### Зафиксированные решения

- **B5/1** — теги не проходят премодерацию: это классификация, а не высказывание.
  Лимиты: 1–30 символов, до 10 уникальных на запись, `trim`, дедуп без учёта регистра,
  пустые отбрасываются; превышение — 400, а не молчаливое обрезание.
- **B5/2** — связь с оценкой/рецензией ставится только по явному `watchId` в теле запроса
  на создание оценки или рецензии. Автопривязки нет: при нескольких просмотрах непонятно,
  к какому приклеивать. Ссылки живут в `Watch` (`ratingId`, `reviewId`), схемы `Rating`
  и `Review` не меняются. Одна цель — одна запись: прежняя привязка у других записей
  этого фильма снимается.
- **B5/3** — дневник публичный по умолчанию, но владелец может его закрыть
  (`PATCH /api/watches/settings`). Закрытый отдаётся только владельцу и админу.
- **B5/3b** — счётчик `watchesCount` на фильме при закрытом дневнике **продолжает
  считать** эти записи: это агрегатное число без имён, и приватность закрывает список,
  а не глобальную статистику. Решение принято агентом по умолчанию; если нужно иначе —
  это один фильтр в `films.routes.js`.
- **B5/4** — `isRewatch` ставит пользователь. Автоопределение ломалось бы на вводе старых
  просмотров задним числом: «уже есть запись» там ничего не значит.
- **B5/5** — событие `watch` в ленту не создаётся: дневник — память, а не сигнал,
  и пересмотры не должны забивать поток. `Event.type` расширять не понадобилось.
- **B5/6** — `watchesCount` публичный и считает **все** записи, включая пользователей
  с `weight: 0`: дневник не гейтится и не взвешивается, анти-накрутка живёт в агрегатах
  оценок, а сортировки по просмотрам нет. Это единственное место, где мы сознательно
  не применяем `weight`-фильтр, и это записано явно.
- **B5/7** — миграция нужна: `counters.watches` проставляется явно. Дополнительно
  `counterMaintenance` пришлось научить считать `watches`, иначе `$set: { counters }`
  в `migrate-counters`/`reconcile-counters` молча стёр бы поле.
- **B5/8** — оценка **не** создаёт запись дневника автоматически: дата «сегодня» была бы
  ложью о реальном просмотре, а ложные данные хуже отсутствующих. Симптом «оценил, а в
  дневнике пусто» закрывается в F-серии черновиком с подтверждением даты.
- **«Лист» из пометки B4** — имелся в виду дневник (это B5/8 выше). Watchlist — это B6,
  и там автодобавление просмотренного было бы багом; в B5 watchlist не трогали.
- **Индексы `Watch`** — `{ userId, watchedAt: -1 }` (своя лента), `{ filmId }` (счётчик
  фильма), `{ userId, filmId }` (проверки `watchId`).

### Код и тесты

- `src/models/Watch.js` — новая коллекция; `src/routes/watches.routes.js` — API;
  `src/utils/watchLink.js` — привязка к оценке/рецензии.
- `src/models/User.js` — `counters.watches` и `diaryPrivate`; `src/utils/counters.js` —
  `watches` в белом списке; `src/utils/counterMaintenance.js` — считает дневник.
- `scripts/migrate-b5-watches.js` — идемпотентная миграция с `--dry-run`.
- `tests/watch-diary.test.js` — 23 теста: создание без оценки, пересмотры, дата в прошлом
  и будущем, удаление своё/чужое, пагинация, публичность и приватность, теги и лимиты,
  отсутствие события, привязка оценки и рецензии, чужой `watchId`, `watchesCount`
  с `weight: 0`, миграция. Запуск: `npm run test:watches`.
- `tests/counters.test.js` — в ожиданиях появился `watches`; `tests/poster.test.js` —
  счётчик дневника заглушён (файл работает без Mongo).
- Итого **193 теста**, все зелёные.

### Миграция

```bash
node scripts/migrate-b5-watches.js --dry-run   # только считает
node scripts/migrate-b5-watches.js             # проставляет counters.watches и diaryPrivate
```

Счётчик выставляется по факту — по количеству записей `Watch`, а не просто в ноль,
поэтому скрипт безопасно запускать и после появления первых записей.

## 5.3 — B4: гейтинг рецензий, серверный ratingId, isSpoiler

**Дата: 29.10.2026.**

### Смысл

Рецензия — ступень выше комментария. Vibe даёт право комментировать (B3), full — право
писать рецензию: одна цифра → комментарий, 15 критериев → рецензия. Гейт стоит до
валидации тела и до модерации, как в B3: vibe-only пользователь получает 403, а не 400
«текст короткий».

### API

- `POST /api/reviews` требует `Rating` с `{ userId, filmId, completeness: 'full' }`.
  Нет — **403 `FULL_RATING_REQUIRED_FOR_REVIEW`**.
- `ratingId` больше не принимается из тела: сервер берёт `_id` своей оценки. Старый
  фронт, который его присылает, продолжает работать — значение игнорируется.
- `isSpoiler` — булево, `default: false`; сохраняется и отдаётся везде, где отдаётся
  рецензия: создание, `GET /reviews/:filmId`, `GET /reviews/details/:id`,
  `GET /reviews/user`, профиль пользователя, админ-очередь.
- Минимум текста остался **350 символов**: понижение до 10 отклонено заказчиком.
  Максимум 15000 — как было.
- Статус создания остался `200` (не `201`): поведение не менялось, тесты и фронт
  на него опираются.

### Зафиксированные решения

- **B4/1A** — `ratingId` из тела игнорируется всегда. У пары user+film оценка одна
  (`unique`), поэтому у корректного клиента значение совпало бы; а для некорректного
  сервер всё равно берёт своё. Проверка «чужая оценка» стала невозможной и удалена.
- **B4/2** — минимум текста 350. Ниже — это комментарий, для него есть отдельная форма.
- **B4/3** — планка длины едина для создания и будущего редактирования: она живёт
  в схеме `Review`, поэтому правка унаследует её без отдельного кода. Редактирования
  рецензий сейчас нет.
- **B4/4** — фильтра `?spoiler` на бэке нет: `isSpoiler` отдаётся у каждого элемента,
  фильтрует фронт. Параметр можно добавить позже аддитивно.
- **B4/5** — в админ-очереди `isSpoiler` ничего не скрывает: модератор обязан видеть
  текст целиком. Скрытие существует только на публичном фронте.
- **B4/migration** — миграция не нужна: `default: false` в схеме, старые документы
  читаются как `false` при гидрации; в профиле флаг приводится явно (`=== true`).
- **B5/out-of-scope** — автоотметка «просмотрено» и добавление фильма в лист при
  наличии оценки в B4 **не реализованы**: это дневник (B5). Важный факт: такой логики
  в коде не было и нет — существует только числовой счётчик `counters.watchlist`,
  никакой привязки watch к `Rating`. Схема `Review` и `reviews.routes.js` под это
  не трогались.

### Код и тесты

- `src/utils/ratingGate.js` — `findRatingForFilm()` и режим `attachAs` у middleware:
  B4 берёт из найденной оценки `_id` для `Review.ratingId`, а не ищет её второй раз.
- `src/models/Review.js` — добавлено `isSpoiler`, остальное не тронуто.
- `src/routes/users.routes.js` — `isSpoiler` в выдаче профиля: там поля перечисляются
  руками, иначе флаг терялся бы только на профиле.
- `tests/review-gating.test.js` — 15 тестов: отказ без оценки, vibe-only, full, админ,
  `weight: 0`, приоритет 403 над 400, апгрейд vibe → full, игнор `ratingId`, запрос без
  `ratingId`, границы 349/350 и 15000/15001, спойлер во всех выдачах, старая рецензия
  без поля, полный текст в админ-очереди. Запуск: `npm run test:reviews`.
- `tests/regression.test.js` — тест «рецензия не принимает оценку другого фильма»
  заменён: теперь он проверяет 403 без своей full-оценки, потому что подстановка
  чужой оценки больше невозможна.
- Итого **170 тестов**, все зелёные.

Не нужна.

## 5.2 — B3: гейтинг комментариев

**Дата: 29.10.2026.**

### Смысл

Комментировать может только тот, кто оценил фильм — любой оценкой, vibe или full.
Одна цифра 1–10 уже означает «смотрел, у меня есть мнение»; требовать 15 критериев
значило бы превратить обсуждение в клуб избранных. Ответы подчиняются тому же правилу,
иначе обход: «не могу начать тред, зато могу ответить в чужом».

Гейтинг стоит до модерации, а не вместо неё: сначала «есть ли оценка», потом обычный
`pending` → `approved`/`rejected`.

### API

- `POST /api/comments` (и корневой комментарий, и ответ) перед созданием проверяет
  `Rating.exists({ userId, filmId })`. Оценки нет → **403 `RATING_REQUIRED_FOR_COMMENT`**.
- Проверка идёт до валидации тела: без оценки ответ 403, а не 400 «текст длинный».
  Кривой `filmId` остаётся 400 — гейт не подменяет ошибку валидации.
- Валидный, но несуществующий фильм: без оценки 403, с оценкой 404. Порядок намеренный:
  проверка оценки дешевле и для неоценившего верна в любом случае.
- `POST /api/comments/:id/like` не гейтится: лайк — реакция, а не высказывание.
- Отдельного «can-post» эндпоинта нет: фронт смотрит на `userRating` в
  `GET /api/films/:id` (он есть с B1), а 403 — честный fallback при рассинхроне.
- Оценка не обязана быть полной и не обязана иметь `weight > 0`.

### Зафиксированные решения

- **B3/1A** — комментарии, написанные до гейтинга, не трогаем: видимость не меняется,
  поле `legacy` не заводим (схема `Comment` заморожена до B8), миграции нет.
- **B3/2A** — оценка с `weight: 0` считается входом в обсуждение: гейтинг про «смотрел ли»,
  анти-накрутка — про агрегаты. Помеченный аккаунт не получает молчаливого бана на всё.
  Спам в этом случае ловит очередь модерации, а не гейт.
- **B3/3A** — админ не исключение. Цена решения: служебный ответ требует оценки, и она
  войдёт в агрегаты обычным голосом.
- **B3/4A** — фронт определяет доступность формы по `userRating`; отдельного эндпоинта нет.
- **B3/5A** — гонка «vibe и комментарий одновременно» — задача фронта: сначала
  `POST /api/ratings`, потом `POST /api/comments`. Бэк не ждёт и не ретраит, он отвечает
  правду на момент запроса.

### Код и тесты

- `src/utils/ratingGate.js` — `hasRatingForFilm()` и middleware `requireRatingForFilm()`.
  Фильтр по `completeness` параметризован: B4 переиспользует его со значением `'full'`.
- `tests/comment-gating.test.js` — 15 тестов: нет оценки, vibe, full, ответы, свой тред,
  админ, `weight: 0`, лайк, legacy-комментарий, приоритет 403 над 400, кривой `filmId`,
  несуществующий фильм, согласованность с `userRating`, повтор после гонки.
  Запуск: `npm run test:gating`.
- `tests/regression.test.js` и `tests/counters.test.js` — три теста создавали комментарии
  от пользователей без оценки; теперь они сначала ставят оценку (а мок-тест счётчиков
  стабит `Rating.exists`).
- Итого **155 тестов**, все зелёные.

### Миграция

Не нужна: решение B3/1A оставляет историю как есть.

## 5.1 — B2: агрегаты фильма по двум осям

**Дата: 29.10.2026.**

### Смысл

Vibe и полная оценка — две разные оси, и агрегаты этого больше не путают. Средний
вайб считается по всем оценкам: vibe есть у обоих типов. Технический и комбинированный
— только по `completeness: 'full'`: у vibe-оценки там `0`, это маркер «не вычислено»
(DECISION 2A), а не результат. Раньше `$avg` складывал маркер с баллами, и фильм с
тремя полными по 75 и одной vibe показывал средний технический 56.

Ноль остаётся маркером и не превращается в `null`: если полных оценок нет, средний
технический и комбинированный равны `0`, и фронт показывает «пока никто не разобрал
подробно». В списках и топах, наоборот, отсутствующее число отдаётся `null` — там
старый фронт рисует `null` как «—», а `0` нарисовал бы красное «0.0», что читается
как «плохо», а не «не оценено».

### Что изменилось

| Эндпоинт | Изменения |
|---|---|
| `GET /api/films/:id` | `averageVibe` — по всем оценкам; `averageTechnical` и `averageCombined` — только по полным; полных нет → `0`. Новые `vibesCount` (только vibe) и `fullCount`; `votesCount` = все. `averageRating` — алиас `averageTechnical`. |
| `GET /api/films` | те же три средних и счётчики; отсутствующее среднее — `null`; каталог по-прежнему показывает **все** фильмы, неоценённые идут в конце; `sort=new` — по дате добавления. |
| `GET /api/films/top` | в топе только участники оси: по техническому/комбинированному — фильмы с полной оценкой, по вайбу — с любой. Новые `total` (считает участников, а не всю базу) и `fallback` для пустого топа. |
| `GET /api/films/:id/ratings`, `/:id/users` | без изменений: `completeness` отдаётся с B1. |

`weight: { $ne: 0 }` остаётся: оценки с нулевым весом не входят ни в одно среднее,
ни в один счётчик и ни в один топ.

### Округление

Все три средних округляются до десятых одной функцией `roundTenth` — одинаково на
странице фильма, в каталоге и в топе. Раньше каталог и топ отдавали сырое `$avg`.

### Зафиксированные решения

- **B2/1A** — `averageRating` остаётся алиасом `averageTechnical` (им он и был).
  Удаление — вместе с F1, когда новый фронт перестанет его читать.
- **B2/2B** — `sort=new` в `/films` как точка входа для свежих импортов. Nice-to-have:
  решение 6A делает такие фильмы видимыми и без него, поэтому снять `sort=new` можно
  без дыры в контракте.
- **B2/3C** — пустой топ отдаётся пустым (`films: []`, `total: 0`) плюс
  `fallback: { sort: 'vibe', available }`; молчаливой подмены на vibe-топ нет.
- **B2/4A** — `votesCount` = все оценки (vibe + full); разделение — `vibesCount` и
  `fullCount`.
- **B2/5B** — профиль и лента вне B2: бэкенд уже отдаёт `completeness`, «ноль как балл»
  — дефект отрисовки, задача F1. `0` на `null` там не меняем: это отменило бы 2A.

## 5.0 — P1: двухступенчатая оценка (vibe → full)

**Дата: 29.10.2026.**

### Модель

- `Rating.completeness`: `'vibe' | 'full'`, по умолчанию `'full'` для обратной совместимости.
- `Rating.scores` больше не `required` на уровне схемы: полноту по-прежнему проверяет
  роут, а pre-validate не даёт сохранить full без 15 критериев.
- `technicalScore` и `combinedScore`: `min: 0`; `0` — маркер «не вычислено»
  (`// DECISION: 2A`).
- `Rating.vibeCreatedAt` + индекс `{userId, vibeCreatedAt}` для дневного капа.
- `User.counters.vibes`; служебное `User.vibeWindow` (не отдаётся наружу).
- `Event.type` расширен значением `'vibe'`.

### API

- `POST /api/ratings` принимает два вида payload:
  - `{ filmId, vibe }` — vibe-оценка (`technicalScore = 0`, `combinedScore = 0`,
    `scores` отсутствует);
  - полный payload, как раньше; старый фронт работает без изменений.
- Апгрейд vibe → full — та же запись (`_id`, `createdAt`, уникальность `(userId, filmId)`);
  `completeness` меняется на `'full'`.
- `// DECISION: 1A` — даунгрейда нет: vibe-запрос к full-оценке → `400 ALREADY_FULL_RATING`.
- `// DECISION: 3A` — `vibe` можно изменить при апгрейде; если поле не пришло,
  берётся вайб из существующей записи.
- `weight` при апгрейде сохраняется из существующей записи (включая `0`),
  `ip` обновляется, `createdAt` не меняется.
- Дневной кап: 50 новых vibe за скользящие 24 часа, проверяется атомарной
  pipeline-операцией по `User.vibeWindow` до создания; 51-й → `429 VIBE_LIMIT_REACHED`
  с `details: { limit, window: '24h', retryAt }`. Апгрейд капом не ограничен.
- `completeness` отдаётся везде, где API возвращает рейтинг: создание/обновление,
  `userRating`, `/ratings/user`, `/films/:id/ratings`, `/films/:id/users`,
  `/ratings/:id/details`, профиль пользователя.

### Геймификация

- Vibe: **+2** балла, `counters.vibes +1`, событие `type: 'vibe'`
  (`score: null`, `metadata: { vibe, completeness: 'vibe' }`), достижения не пересчитываются.
- Full: **+8** при апгрейде (суммарно 10), `counters.ratings +1`, `counters.vibes −1`,
  событие `'rating'`, `updateAchievements`. Новая полная оценка — как раньше: +10 (+20 админу).
- Прогресс достижений: `effective = counters.ratings + counters.vibes / 5`;
  пороги 20 / 50 / 100 / 200 (константы `RATING_20`, `RATING_50`, `RATING_100`, `RATING_200`).
- Новая ачивка `FIRST_VIBE` («Первое впечатление»); `FIRST_RATING` — только за первую
  полную; `FIRST_FRAME` — первые 100 зарегистрированных **и** хотя бы одна полная.
- Существующие достижения не отбираются: `updateAchievements` только добавляет новые.

### Миграция

- `scripts/migrate-p1-vibe-ratings.js`: `Rating` без `completeness` → `'full'`,
  `User` без `counters.vibes` → `0`. Идемпотентно, есть `--dry-run`.
- Запускать до деплоя; порядок и ожидаемый вывод — в README, §11.

## 4.1 — постеры перестают быть заглушками

**Дата: 26.10.2026.** Симптом: у пользователей из России вместо постеров заглушка, хотя
прокси на бэкенде «настроен». Разбор показал три независимые причины — каждой хватило бы
для пустых карточек.

### Что было не так

| Причина | Как проявлялась |
|---|---|
| В проде `IMAGE_PROXY_BASE_URL=https://cinephilium-frontendnew.vercel.app` (домен фронтенда) | `posterUrl` вёл на `/api/tmdb-image` **Vercel**, где такого маршрута нет: SPA отвечает `200 text/html`, браузер не получает картинку |
| Легаси-поле `poster` хранило прямой `https://image.tmdb.org/...` | Старый клиент (и любой потребитель API) рендерил его напрямую; в РФ `image.tmdb.org` отдаёт обрыв соединения |
| Прокси постеров стоял **после** `globalLimiter` (200/мин), а ключом лимита был `req.ip` = IP edge-ноды Cloudflare | Один лимит на тысячи людей: 20–40 картинок на страницу выжигали квоту, и постеры получали `429` вместе с API. Проверка: `remaining` в заголовке `ratelimit` менялся от запроса к запросу при одном и том же клиенте |

### Что сделано

- `src/utils/poster.js`: база прокси нормализуется (хвостовой `/`, случайный `/api`); если
  `IMAGE_PROXY_BASE_URL` не задан — берётся origin входящего запроса (всегда бэкенд), а если
  в переменной оказался домен фронтенда и запрос пришёл с другого домена — тоже origin запроса.
  Легаси-`poster` с прямой ссылкой TMDB конвертируется в прокси-адрес, `posterPath`
  восстанавливается на лету.
- `src/config/env.js`: значение проверяется и нормализуется на старте, при совпадении с
  доменом фронтенда в логах появляется предупреждение.
- `src/middleware/security.js`: `clientIp()` для всех лимитов — `cf-connecting-ip` →
  `x-real-ip` → `req.ip`; добавлен отдельный `imageLimiter` (1200/мин).
- `src/app.js`: прокси постеров (`/api/tmdb-image`, `/api/poster/:size/*`) монтируется
  **до** `globalLimiter` и общий лимит не выжигает.
- `api/tmdb-image.js`: LRU-кэш байтов в памяти инстанса (48 МБ), склейка одновременных
  запросов одной картинки, `ETag` + `If-None-Match` → `304`, `Content-Length`.
  Повторный постер отдаётся за миллисекунды и не идёт в TMDB.
- `tests/poster.test.js`: 15 тестов — нормализация базы, конвертация легаси-постера,
  origin из запроса, домен фронтенда в переменной, кэш/`304`, 210 запросов к прокси без `429`.
- Логи: `GET /` теперь отвечает `200` (Render и мониторинги дёргают корень, раньше каждый
  health-check писал 404 со стеком), а ожидаемые `4xx` (истёкший токен, битый id, лимит)
  пишутся компактным `[WARN]` без стека. `5xx` по-прежнему `[ERROR]` со стеком.

### Проверено

- `image.tmdb.org` из РФ (ноды check-host ru1–ru3, kz1): `Connection refused`;
  тот же постер через `https://<бэкенд>/api/tmdb-image` — `200 image/jpeg` из ru1–ru3.
- Локально: `200 image/jpeg`, повторный запрос `304`, `ratelimit: limit=1200`.
- Лимит по-прежнему режет злоупотребления: 201-й запрос с одного `cf-connecting-ip`
  к API получает `429`, соседний IP — `200`.

### Что сделать на проде

1. В Render **удалить** `IMAGE_PROXY_BASE_URL` (или поставить `https://cinephilium-backend.onrender.com`).
2. Задеплоить бэкенд, затем фронтенд (ссылки на постеры приходят из API).
3. Проверить: `curl -I "https://<бэкенд>/api/tmdb-image?size=w500&path=%2F<файл>.jpg"` → `200 image/jpeg`.
4. `node scripts/migrate-posters.js` не обязателен: `posterPath` теперь чинится на чтении,
   но прогнать его всё равно полезно, чтобы база была в порядке.

## 1. Бэкенд

### 1.1 Единый обработчик ошибок

**Было:** ошибки разлетались как попало — 404 от Express в HTML, `CastError` из Mongo давал 500,
`ValidationError` тоже 500, тело ошибки в разных роутах имело разную форму (`{ error: '...' }`,
`{ message: '...' }`).

**Стало:** `src/middleware/errorHandler.js` + `src/utils/errors.js`.

- `AppError` и наследники (`ValidationError`, `UnauthorizedError`, `ForbiddenError`,
  `NotFoundError`, `ConflictError`) несут `statusCode` и машиночитаемый `code`.
- Ответ всегда: `{ "error": { "code", "message", "details?" } }`.
- `CastError` → 400, дубликат `11000` → 409, `JsonWebTokenError` → 401,
  `entity.parse.failed` (битый JSON) → 400 `INVALID_JSON`, `entity.too.large` → 413.
- 404 на неизвестный маршрут — JSON (`notFoundHandler`).

Ключевой фрагмент (`src/middleware/errorHandler.js`):

```js
} else if (err.type === 'entity.parse.failed') {
  statusCode = 400;
  code = 'INVALID_JSON';
  message = 'Некорректный JSON в теле запроса';
}
```

### 1.2 Аутентификация v3: access + refresh + сессии

**Было:** один JWT на 7 дней в `localStorage`, без отзыва, без обновления.

**Стало:**

- `utils/jwt.js` — два разных секрета и два типа токенов:
  `signAccessToken()` (`expiresIn: JWT_ACCESS_TTL`, по умолчанию 15m, `type: 'access'`) и
  `signRefreshToken()` (`JWT_REFRESH_TTL_DAYS`, по умолчанию 30 дней, `type: 'refresh'`, `jti`).
  Оба подписываются `HS256`, `verify*` проверяют `type` — access нельзя подсунуть вместо refresh.
- `models/Session.js` — серверная сессия: `tokenHash` (SHA-256 refresh-токена), `userAgent`, `ip`,
  `expiresAt` с TTL-индексом (`expireAfterSeconds: 0`).
- `routes/auth.routes.js` — `issueTokens()` создаёт сессию, кладёт refresh в HttpOnly cookie
  (`utils/cookies.js`) и возвращает только `accessToken`.
- `POST /api/auth/refresh` — ротация: старый хеш атомарно заменяется новым
  (`Session.updateOne({ _id, tokenHash: old }, { $set: { tokenHash: new } })`), при
  `modifiedCount !== 1` сессия считается отозванной → 401. Повторное использование старой
  cookie не проходит.
- `POST /api/auth/logout` — удаляет сессию и чистит cookie, `POST /api/auth/logout-all` — все сессии.
- Cookie: `httpOnly`, `path=/api/auth`, `SameSite=None` в проде (cross-site vercel → onrender),
  `Secure` при `NODE_ENV=production`. `COOKIE_DOMAIN` больше не хардкодится как `localhost`.

### 1.3 Подтверждение email и сброс пароля

**Было:** регистрация сразу выдавала токен.

**Стало:**

- `POST /api/auth/register` создаёт пользователя с `emailVerified: false` и отправляет
  6-значный код (`updateVerification()` → `mailer.sendVerificationCode`). В БД лежит только
  `hashToken(code)` (SHA-256), TTL `EMAIL_CODE_TTL_MIN` (10 минут), 5 попыток ввода,
  повторная отправка с cooldown `EMAIL_RESEND_COOLDOWN_SEC` (60 с) и лимитом
  `EMAIL_RESEND_MAX_PER_HOUR` (3 в час).
- `POST /api/auth/verify-email` сверяет хеш кода и выдаёт пару токенов.
- `POST /api/auth/resend-verification` — повторная отправка с теми же лимитами.
- `POST /api/auth/forgot-password` — генерирует 32-байтный токен, хранит только его SHA-256,
  TTL 30 минут, письмо со ссылкой `${CLIENT_URL}/reset-password?token=...`.
  Ответ всегда одинаковый (`Если email существует, письмо отправлено`) — нет user enumeration.
- `POST /api/auth/reset-password` — принимает `token` + `newPassword`, проверяет срок и
  одноразовость, меняет пароль и **удаляет все сессии** (`Session.deleteMany`).
- `middleware/auth.js`: `requireVerified` пускает к записи только `emailVerified: true`.

Письма отправляет `src/services/mailer.js` (nodemailer). Если SMTP не настроен:
в dev ссылка/код печатаются в консоль (`[DEV] password reset link ...`), в production
бросается `EMAIL_SEND_FAILED` и ошибка уходит в лог.

### 1.4 Модерация

Требования к правам переехали в middleware (`authenticate` + `isAdmin`). Исправлены две дыры:

- `GET /api/reviews/details/:id` отдавал рецензию на модерации любому, кто знал id
  (`src/routes/reviews.routes.js`). Теперь `status !== 'approved'` виден только автору и админу,
  остальным — 404.
- `GET /api/users/:id` отдавал чужие черновики рецензий и комментариев. Теперь
  `statusFilter = isOwnProfile || isAdmin ? {} : { status: 'approved' }`
  (`src/routes/users.routes.js`).

Повторное одобрение больше не фармит награды: в `src/routes/admin.routes.js` побочные эффекты
(очки, событие, достижения, счётчик) выполняются только при переходе статуса
`before.status !== 'approved'`.

### 1.5 Счётчики

**Было:** количество оценок/рецензий считалось `countDocuments` в каждом запросе, топ пользователей
делал три `$lookup` на каждый профиль.

**Стало:** денормализованные счётчики `User.counters` (`ratings`, `reviews`, `reviewsApproved`,
`comments`, `commentsApproved`, `likesReceived`, …), инкремент через `utils/counters.js`:

```js
const path = `counters.${field}`;
if (delta < 0) {
  return User.updateOne(
    { _id: userId, [path]: { $gte: Math.abs(delta) } },   // не уходим в минус
    { $inc: { [path]: delta } }
  );
}
```

Топ пользователей (`src/routes/top.routes.js`) больше не делает `$lookup` — читает `counters`.

### 1.6 Постеры

**Было:** в БД хранился полный URL `poster` на `image.tmdb.org`.

**Стало:** хранится `posterPath` (например `/abc.jpg`), URL собирается на чтении
(`src/utils/poster.js`):

```js
const base = process.env.IMAGE_PROXY_BASE_URL;
if (!base) return `https://image.tmdb.org/t/p/${size}${posterPath}`;
return `${base}/api/tmdb-image?size=${size}&path=${encodeURIComponent(posterPath)}`;
```

- `api/tmdb-image.js` — прокси с белым списком размеров, проверкой `path`
  (запрет `..`, `//`, не-ASCII), таймаутом 10 с и лимитом 5 МБ.
- Прокси смонтирован и в Express (`src/app.js`), и как Vercel-функция.
- Для старого фронта оставлено legacy-поле `poster` — оно заполняется тем же URL.
- `scripts/migrate-posters.js` переносит старые записи `poster` → `posterPath`.

### 1.7 Согласия при регистрации

**Требование:** данные не должны попадать в БД до согласия на обработку персональных данных и cookie.

**Реализация:**

- `src/models/User.js` — вложенная схема `consent` (`personalData`, `cookies`, `version`,
  `acceptedAt`, `ip`) и поле `registeredIp`.
- `src/routes/auth.routes.js` — проверка стоит **до** первого обращения к БД:

```js
const consent = req.body.consent;
if (!consent || consent.personalData !== true || consent.cookies !== true) {
  throw new ValidationError('Нужно согласие на обработку персональных данных и использование cookie');
}
const { email, password, nickname } = req.body;
const existingEmail = await User.findOne({ email });   // только после проверки
```

Тест `tests/regression.test.js` проверяет не только 400, но и что документ не создан
(`User.countDocuments(...) === 0`).

### 1.8 Анти-накрутка оценок

**Проблема:** ферма аккаунтов могла раздуть среднюю оценку. Воспроизведение до фикса: 10 аккаунтов
с одного IP → средняя 100, фильм №1 в топе.

Причины:

1. `authLimiter` имел `skipSuccessfulRequests: true` — успешные регистрации вообще не считались,
   лимит видел только ошибки.
2. На оценки не было лимита по IP.
3. Все голоса были равны, никакой «подозрительности» не существовало.

Что сделано:

- `middleware/security.js` — `registerLimiter` (10 регистраций/час на IP, считает и успешные)
  и `ratingLimiter` (40 оценок/час на IP).
- `models/User.js` — `trustWeight` (0..1, по умолчанию 1), `flagged`, `registeredIp`
  + индексы `{ registeredIp, registeredAt }` и `{ flagged }`.
- `models/Rating.js` — `weight` (0..1) и `ip`. Вес копируется из аккаунта при сохранении:

```js
weight: typeof req.user?.trustWeight === 'number' ? req.user.trustWeight : 1,
ip: req.ip || ''
```

- Агрегаты игнорируют помеченные голоса. В `src/routes/films.routes.js` `$lookup` переписан на
  пайплайн с фильтром:

```js
{
  $lookup: {
    from: 'ratings',
    let: { filmId: '$_id' },
    pipeline: [
      { $match: { $expr: { $eq: ['$filmId', '$$filmId'] }, weight: { $ne: 0 } } },
      { $project: { technicalScore: 1, vibe: 1, combinedScore: 1, weight: 1 } }
    ],
    as: 'ratings'
  }
}
```

То же для деталей фильма (`$match: { filmId, weight: { $ne: 0 } }`) и для топа пользователей
(`$match: { flagged: { $ne: true } }`).

- `scripts/flag-sybil-accounts.js` — детектор: группирует пользователей по `registeredIp` за окно
  времени, при `count >= 5` за час ставит `trustWeight = 0` и `Rating.weight = 0`.
  Есть `--dry-run` и `--unflag`.

Проверка в тестах: после пометки у фильма `votesCount: 0`, он исчезает из топа, ферма — из топа
пользователей.

### 1.9 Совместимость с текущим фронтендом

Фронт ожидал контракт, части которого в API не существовало. Добавлено без ломки старого:

| Что | Где |
|---|---|
| `GET /api/users/nickname/:nickname` — компактный lookup `{ _id, id, nickname, avatar }` | `src/routes/users.routes.js` |
| `GET /api/users/me/achievements` — `{ earned, possible, totalPoints, progress }` | там же |
| `counters` в ответе профиля | там же |
| legacy-поле `poster` = готовый URL | `src/utils/poster.js` |
| алиас `/api/poster/:size/*` для старой схемы ссылок | `src/app.js` |
| `SameSite=None` при `Secure` для cross-site cookie | `src/utils/cookies.js` |

### 1.10 Исправленные баги (найдены тестами)

1. Поиск по названию собирал `RegExp` из пользовательского ввода: `?title=[` → 500, а `(a+)+$` — ReDoS.
   Теперь `escapeRegex()`.
2. Сбой TMDB в импорте давал 500; теперь 404 «фильм не найден» и 502 «сервис недоступен».
3. `textReview` длиннее 2000 символов → 500 от валидатора Mongoose; теперь 400.
4. Ответ на комментарий можно было привязать к комментарию другого фильма; теперь сверяется `filmId`.
5. `limit` в `/api/films` не был ограничен; теперь максимум 100, `page` чинится от отрицательных.
6. `likesReceived` в топе считался и тут же удалялся `$project` — поля не было в ответе.
   Теперь оно живёт в `counters` и отдаётся.
7. CORS: `origin: 'строка'` не сверялся с запросом (заголовок отдавался всем). Теперь список
   `CORS_ORIGIN` через запятую.
8. `/api/tmdb-image` был только Vercel-функцией, в Express — 404. Смонтирован.
9. Кривой id в админ-роутах (`/admin/comments/not-an-id/approve`) → 500; теперь 400 благодаря
   `CastError` в обработчике.

## 2. Фронтенд

### 2.1 HTTP-клиент и обновление токена

`src/api/client.js` переписан:

- `baseURL` из `REACT_APP_API_URL`, `withCredentials: true` (нужно для refresh-cookie).
- access-токен в `accessToken` (+ дублируется в старый ключ `token`, чтобы не править 20 мест
  в компонентах).
- при 401 — single-flight refresh и один ретрай исходного запроса; если refresh не удался,
  сессия чистится и пользователь уходит на `/login`.
- ошибки нормализуются: `{ error: { message } }` превращается в строку, поэтому старые
  `err.response?.data?.error` продолжают показывать текст, а не `[object Object]`.
- `logout()` отзывает сессию на сервере, а не только чистит `localStorage`.

### 2.2 Вход и регистрация

`src/pages/LoginPage.jsx`: три состояния — `login`, `register`, `verify`.

- логин сохраняет `accessToken`;
- регистрация больше не ждёт токен: показывается экран ввода 6-значного кода из письма,
  с кнопкой «Отправить код ещё раз»;
- пароль — минимум 8 символов (как на сервере).

### 2.3 Сброс пароля

- `src/pages/ForgotPasswordPage.jsx` (`/forgot-password`) — email → `POST /api/auth/forgot-password`,
  нейтральное сообщение об отправке.
- `src/pages/ResetPasswordPage.jsx` (`/reset-password?token=…`) — новый пароль + подтверждение,
  проверка длины и совпадения, обработка битой ссылки.
- Ссылка «Забыли пароль?» на странице входа.

### 2.4 Согласия и политика

- В форме регистрации два обязательных чекбокса (персональные данные, cookie) — без них кнопка
  не отправляет запрос; согласия уходят в API (`consent: { personalData, cookies, version }`).
- `src/pages/PrivacyPage.jsx` (`/privacy`) — описание обрабатываемых данных и cookie
  (шаблон, требует юридической вычитки).

### 2.5 Остальное

- `TopUsersPage` — формат `{ items, pagination }` и статистика из `counters`.
- `useActivityEvents` — лента только читается; фронт больше не дублирует события через
  несуществующий `POST /events`.
- `ProfilePage` — достижения из `earned`, выход через серверный `logout`.
- `poster`/`posterUrl` — работают оба, потому что бэкенд заполняет legacy-поле.

## 4. Миграции

Код переживает отсутствие новых полей (проверки через `$ne`/`$exists`), но для корректных отчётов
и работы детектора данные надо привести к новой форме. Порядок — в README, раздел «Миграции».
Коротко:

1. `node scripts/backfill-email-verified.js` — иначе **старые пользователи не смогут войти**
   (логин требует `emailVerified: true`, а у старых записей этого поля нет).
2. `node scripts/migrate-counters.js` — заполнить `counters`, иначе достижения и топ покажут нули.
3. `node scripts/migrate-posters.js` — перенести `poster` → `posterPath`.
4. `node scripts/backfill-anti-farm.js` — `weight`, `ip`, `trustWeight`, `flagged`, `registeredIp`,
   `consent` + индексы.
5. `node scripts/reconcile-counters.js` — сверка счётчиков с фактическими документами.

Все скрипты идемпотентны, у новых есть `--dry-run`.

## 5. Известные ограничения

- Распределённая ферма (много IP, одноразовые почты) детектором по IP не ловится — нужны CAPTCHA
  и репутация домена.
- Баллы помеченных аккаунтов не обнуляются (они просто исчезают из рейтинга).
- Нет удаления оценок/рецензий, поэтому награды не откатываются.
- `updateAchievements` тихо логирует ошибку, если соединение с Mongo ещё не готово.
- `useCriticData` на фронте завязан на захардкоженный никнейм и мок-данные.
- У фронтенда нет автотестов, только сборка.
